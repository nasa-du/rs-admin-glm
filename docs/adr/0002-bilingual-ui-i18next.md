# 界面双语：zh-CN / en 与 i18next

管理后台的受众当下虽以中文为主，但产品存在对外/出海的可能性，故界面文案自第一天起按 zh-CN / en 双语维护，而不是先做单语言全量中文、将来再补。选定 i18next 全家桶（`react-i18next` + `i18next-browser-languagedetector`）。决议过程与完整参数见 [#4](https://github.com/nasa-du/rs-admin-glm/issues/4)。

## Considered Options

- **单语言全量中文（拒绝）**：实现最省，且「将来再加双语、届时包装字符串的成本与现在做相同」成立——但出海方向明确，双语纪律（两份 locale 同天提交、组件内禁裸字符串）现在建立，避免英文文案欠账越滚越大。
- **lingui（拒绝）**：编译期提取的优势要在文案量巨大时才兑现，管理后台的规模撑不起多一条工具链。
- **手写最小字典（拒绝）**：双语下插值、复数、检测、持久化全要自建，省下的那点依赖不值。

## Consequences

- 后端 API 只出语义错误码与枚举，**所有用户可见文案归前端 locale 文件**，服务端永远不感知 locale——将来加语言后端零改动。
- 语言记忆走 localStorage（不进 cookie）；检测链 localStorage → 浏览器语言 → 回退 `zh-CN`。
- 新增界面文案的固定成本翻倍（两份文件），由 review 纪律兜底，不上 lint 工具。
- 出海兑现时，新增 locale 是纯前端加文件；若出海方向最终放弃，删掉 `en` 与切换器即可退回单语言——本决策贵在纪律建立，不在框架锁定。
